# 技术细节

## 一、根因（实测确认，不是推测）

Windows 通过一个"网络签名"来识别网络，其中**决定性的属性是默认网关的 MAC 地址**，它和每个保存的网络配置一起存着：

```
HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\NetworkList\Signatures\Unmanaged\<SIGNATURE>
        DefaultGatewayMac = <6 字节>
```

在开发机上实测：**同一台手机、连续两次网络共享**，产生了两条不同指纹：

| 保存的网络 | 创建时间 | 网关 MAC |
|---|---|---|
| `网络` | 2026-10-09 | `70-3A-A6-AA-30-02` |
| `网络 2` | 2026-10-09 | `68-4A-AE-37-1C-F1` |

安卓**每次开共享都会重新随机化 RNDIS 网卡的 MAC**。Windows 看到新的网关 MAC，就判定这是一个全新网络，于是再存一个配置。名字之所以是自动生成的「网络 N」，是因为这条连接"看起来像有线网"（`NameType = 6`）又没有 DHCP 域名，Windows 只能退回默认命名。

### 两个重要推论

**1. 这件事无法"阻止"，只能"接管"。**

签名的后 64 位十六进制是网关指纹的私有哈希。我验证过所有能想到的候选算法（对 MAC 各种格式做 SHA-256/SHA-1、各种 GUID 组合等 **157 种变体**），**没有一个能复现它**，所以无法预先在注册表里"种"一个配置。

但**有效**的做法是：在 Windows 刚建好配置的瞬间把它改名。这个注册表写入会被 NLA 和设置界面**立即识别**，不需要重启任何服务（Windows 11 22631 实测）。

**2. 网关 MAC 就是手机自己。**

会话期间网关 MAC 等于手机 RNDIS 网卡的 MAC。本工具用这一点来**确证**"这确实是一台手机"，而不是靠"MAC 看起来像随机"这种猜测。

> 普通有线网络也会被 Windows 命名为「网络 N」，原因完全相同。但**这类配置本工具永远不会碰**——见[安全说明](安全说明.md)。

## 二、怎么识别手机、怎么决定名字

不猜、不用启发式：

| 步骤 | 依据 | 说明 |
|---|---|---|
| 1 | **USB 厂商 ID** | 如 vivo/iQOO=`2D95`、小米=`2717`、Google=`18D1`、三星=`04E8`（可配置列表）|
| 2 | **真实父设备**（`DEVPKEY_Device_Parent`）| 先把网卡的网络 GUID 解析到它的 USB 实例，再向上取父设备，**USB 序列号就在父设备上** |
| 3 | **型号名** | 安卓只在**「传输文件」(MTP) 模式**下上报自己的市场名；那条记录是共享同一父设备序列号的兄弟接口，因此能精确对上 |
| 4 | **网关 MAC** | 确证"这次会话就是那台手机"。只有被确证过的 MAC 才会被操作 |

### 为什么不用 USB 端口来区分？

**两台不同手机插在同一个 USB 口上，`LocationInformation` 完全相同。** 开发过程中这导致过一台手机被命名成另一台的名字。

所以**主键是序列号**；端口只在"该端口上恰好只有一台设备上报了型号"时作为兜底。

### 命名优先级

```
config.json 里的 DeviceRules   （按 Vid / ModelLike / SerialLike 匹配 → 你指定的名字）
        │
        ▼  没匹配到规则
这台设备之前学到的名字（存在 state.json）
        │
        ▼  没见过
手机自己上报的型号名                       例如 "Pixel 8"
        │
        ▼  手机从没上报过型号
DefaultName                              例如 "USB Tethering"
```

**永远不会产生「网络 N」。** 如果两台手机会得到同一个名字，第二台自动加 ` 2` 后缀，避免 Windows 又开始编号。

### 设备身份的三层结构

```
USB\VID_2D95&PID_600A&MI_00\6&1EB7303F&1&0000     ← RNDIS 接口（网卡）
    └─ USB\VID_2D95&PID_600A\SERIALNUMBER123      ← 父设备，携带 USB 序列号（身份主键）
USB\VID_2D95&PID_6012&MI_00\6&1EB7303F&1&0000     ← MTP 接口（另一模式才出现）
    └─ USB\VID_2D95&PID_6012\SERIALNUMBER123      ← 同一个序列号 → 能关联到型号名
```

接口路径最后一段（像 `6&1EB7303F&1&0000`）是**端口路径，会随插口变化**，绝不能当身份用。

## 三、工作原理与架构：事件驱动、零轮询

只有一个计划任务 `UsbNetFix-OnPhonePlug`，带 4 个触发器：

| 触发器 | 触发时机 |
|---|---|
| **Kernel-PnP 事件 410 / 400** | USB 设备启动/配置完成（手机的 RNDIS 网卡出现）|
| **NetworkProfile 事件 10000-10002** | Windows 创建 / 变更 / 删除网络配置 |
| **开机触发**（延迟 30 秒）| 每次开机后兜底 |
| **每日一次** | 万一事件漏了的最后保险 |

每次运行都是一个**短命进程**：检查当前状态 → 该改就改 → 退出。**没事发生就完全不运行。**

### 为什么要短命进程而不是常驻守护进程？

开发期间我确实先写了常驻 watcher，但它**被宿主环境反复回收**（长时间运行的子进程不稳定）。改成"短命进程 + 事件触发"后可靠性大幅提升，而且空闲成本为零。

### 那个 Kernel-PnP 触发器为什么不能精确到设备？

Windows 事件查询对 `EventData` **只支持等值比较**（用 `contains()` 会被拒绝：`The specified query is invalid`），而 USB 实例路径会随插口变化。所以只能按 `EventID=410/400` 粗筛——**其他 USB 设备也会触发一次运行**，但脚本会在半秒内发现没有手机并退出。

NetworkProfile 触发器是必要的补充：实测出现过**手机重插时没有产生新的 PnP 事件**，全靠网络配置事件救回来。

### 实测资源占用

| 场景 | 耗时 | 说明 |
|---|---|---|
| 没插手机 | **0.52 秒** | 在任何等待之前就退出，不写日志 |
| 插着手机 | **9.5 秒** | 其中 8 秒是有意为之的等待（等 Windows 确定配置）|
| 峰值内存 | ~180 MB 工作集 | PowerShell 解释器本身的基线，进程退出即释放 |
| 空闲 CPU | **0** | 无轮询、无常驻进程 |

### 各阶段耗时明细

| 操作 | 耗时 |
|---|---|
| `NP-GetGatewayMac`（ARP）| 741 ms |
| `NP-GetInstanceIdForAdapter` | 451 ms |
| `Get-NetAdapter` | 293 ms |
| `Get-NetConnectionProfile` | 117 ms |
| `NP-GetProfiles`（读注册表）| 58 ms |
| `NP-GetState`（读 state.json）| 46 ms |

事件触发时只有 1 次运行，所以这些开销**一天也就几次**。

### 修改前的对比

改成事件驱动之前是每分钟轮询一次：**1440 次/天**、约 12 秒 CPU/天，全部是空转。现在空闲时**零运行**。

## 四、两种目录布局都支持

程序本身不依赖固定路径，以下两种都能直接运行：

```
平铺布局（发布包解压后的样子）
    <安装目录>\
        UsbNetFix.cmd / .ps1
        usbnet-fix.ps1
        netprof-lib.ps1
        ...
        config.json
        state.json         ← 运行时生成
        log\  backup\      ← 运行时生成

lib 布局（deploy.ps1 产生的样子）
    <安装目录>\
        UsbNetFix.cmd / .ps1
        config.json
        lib\
            usbnet-fix.ps1
            netprof-lib.ps1
            ...
```

脚本在运行时探测自己在哪种布局里，并据此定位同伴文件。**放哪个位置、改成什么名字都可以**（路径含空格或中文也验证过没问题）。

### `state.json` 的结构与"有界性"

```json
{
  "Devices": [
    { "DeviceId": "2D95:SERIALNUMBER123", "Name": "Pixel 8",
      "Model": "Pixel 8", "LastGatewayMac": "5a90e662d5ae",
      "LastSeen": "2026-10-12 18:24:14", "Sessions": 8 }
  ],
  "PhoneGatewayMacs": [ "..." ],
  "GatewayMap": { "<mac>": "<DeviceId>" }
}
```

**指纹列表是有意做成有上限的**（默认 64 条）。因为安卓每次会话都给一个新网关 MAC，无上限会无限增长。淘汰最旧的只会导致"那个 MAC 再出现时需要重新学习一次"，而且**每台设备最新的 MAC 永远保留**。实测模拟 100 次会话后列表稳定在上限。

## 五、可选优化空间（未实施，按性价比排序）

| 优化点 | 收益 | 代价 |
|---|---|---|
| `NP-GetGatewayMac` 占 741ms | 单次省 ~500ms | 要改 `arp -a` 解析或加缓存，收益小（现在只在事件时跑）|
| `SettleSeconds` 8 秒 → 4 秒 | 改名更快 | 极慢 DHCP 场景可能改名两次（无害）|
| 编译成单文件 exe | 启动 1.5s → ~0.1s，内存 180MB → ~20MB | 需要构建链，且失去"可直接阅读修改"的优点 |
| 用一次 CIM 调用取网卡+IP+网关 | 省 3 次慢 CIM 调用 | 需重写识别逻辑，风险中等 |

**当前架构在"可靠性 / 资源 / 可维护性"之间是合理平衡**，除非追求极致，否则不建议改。
